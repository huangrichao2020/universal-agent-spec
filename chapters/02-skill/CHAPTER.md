# Chapter 02 · Skill 技能文档

> Skill 是 Agent 的过程性记忆——告诉 Agent "遇到 X 类任务，按这个步骤做" 的结构化文档。
> 积累 Skill 的数量和质量，决定了一个 Agent 的真实能力上限。

---

## 一、Skill 的本质：不是 Prompt，是操作手册

很多人把 Skill 和 Prompt 混为一谈。它们是两种完全不同的东西：

| 维度 | Prompt（人格/系统提示词） | Skill（技能文档） |
|------|---------------------------|-------------------|
| 描述对象 | 身份、风格、价值观 | 具体可执行的操作步骤 |
| 粒度 | 宏观抽象 | 具体到工具名、参数、顺序 |
| 触发方式 | 始终生效，每次调用都带上 | 按需加载，遇到匹配任务才注入 |
| 类比 | 员工性格 | 员工操作手册 |
| 可转移性 | 与 Agent 人格绑定 | **可跨 Agent 复用** |

**一句话区分**：Prompt 回答 "你是谁"，Skill 回答 "这件事怎么做"。

---

## 二、一个优秀 Skill 的解剖结构

以下是从生产级项目（企业级多 Agent 平台）中提炼的 Skill 标准结构。每个 Skill 是一个独立的 Markdown 文件，包含 YAML frontmatter 和 Markdown 正文。

### 2.1 YAML Frontmatter — Skill 的"身份证"

```yaml
---
name: deep-research
description: |
  深度搜索与信息研究技能。当用户需要搜索信息、研究某个主题、
  查找参考资料、了解某个领域、比较多个选项、调查公司背景时触发。
  触发关键词：搜索、研究、查阅、了解、对比、分析、最新消息、
  公司信息、行业报告等。
  不适用于网页交付、文档格式转换或需要真实浏览器交互的任务。
---
```

**关键原则**：
- `name` 是唯一标识，用于路由和匹配
- `description` 是 Skill 被选中的**唯一依据** —— 写得不好，Agent 就找不到这个 Skill
- description 中必须同时包含：**正向触发条件**（什么时候用）和 **反向排除条件**（什么时候不用）

### 2.2 Markdown 正文 — Skill 的"灵魂"

一个完整的 Skill 正文应包含以下模块：

```
# Skill 标题

## 触发与排除条件（Trigger & Exclusion）
  - 必须触发的场景
  - 不应触发的场景 → 指向其他 Skill

## 工具清单（Tool Overview）
  - 本 Skill 涉及的全部工具
  - 每个工具的参数表

## 工作流程（Workflow）
  - 分场景的执行步骤
  - 严格的前后依赖关系

## 质量规则（Quality Rules）
  - 不可违反的约束
  - 常见错误与规避方式
```

## 三、七种经过验证的 Skill 设计模式

以下模式来自真实生产系统的 10+ 个 Skill，每种模式都解决一个具体的工程问题。

### 模式一：工具链依赖模式

**问题**：某些工具必须按顺序调用，跳过前置步骤会直接报错。

**解法**：在 Skill 中用铁律（Iron Rule）强调依赖关系。

```markdown
## 核心工具链

必须严格按以下依赖顺序执行：

Step 1: browser_sandbox_create (创建沙箱)
    → Step 2: universal_code_generation_agent (生成并执行代码)

**铁律：在 browser_sandbox_create 返回有效 sandbox_id 之前，
绝对不能调用 universal_code_generation_agent。**
```

**实战案例**：代码执行 Skill —— 必须先创建沙箱环境，拿到 `sandbox_id`，才能调用代码生成工具。如果跳过第一步，Agent 会尝试在不存在的沙箱中执行代码，导致不可恢复的错误。

### 模式二：人机协作模式（Human-in-the-Loop）

**问题**：某些操作（发送任务、部署服务）不可撤回，必须让用户确认后再执行。

**解法**：将流程拆分为"生成 + 等待确认 + 执行"，严格禁止在同一轮对话中完成。

```markdown
## 场景 A：标准任务调度

**第一轮（生成 + 等待）：**
1. 从用户消息中提取任务名称、描述、负责人
2. 调用 generate_task_card 生成任务卡片
3. 向用户展示任务卡片，询问是否确认发送
4. **停止，等待用户回复 — 本轮结束**

**第二轮（执行用户决策）：**
- 用户确认 → 调用 send_task
- 用户要求修改 → 调整后重新执行第一轮

**关键约束：generate_task_card 和 send_task
绝不能在同一轮对话中调用。**
```

**为什么有效**：LLM 有"一次性完成所有事"的倾向。如果不在 Skill 中明确写"停下来等"，它会在生成任务卡片后直接发送，用户根本没机会检查。

### 模式三：多工具路由模式

**问题**：同一个 Skill 内有多个工具，Agent 不知道什么时候用哪个。

**解法**：在 Skill 中给出明确的决策树。

```markdown
## 选择解析工具

**默认使用 process_document_from_url（轻量快速）。**

满足以下任一条件时，切换到 process_document_with_images：
- 用户提到"图片"、"图文"、"保留图片"
- 源文档是 PPTX（图片通常是核心内容）
- 用户要求"完整提取"或"保持原样"
- 目标文档需要包含图片
```

**实战案例**：文档处理 Skill 有两个解析工具。默认用轻量版（纯文本），只在明确需要图片时才切换到重量版。没有这个路由规则，Agent 会随机选择，导致不必要的资源消耗或图片丢失。

### 模式四：深度研究分阶段模式

**问题**：搜索类任务容易"浅尝辄止"，Agent 搜一两次就开始写输出。

**解法**：强制分阶段执行，要求最低搜索广度。

```markdown
## 研究方法论

### 阶段一：广度探索
用宽泛关键词了解全貌，识别需要深入的子主题。

### 阶段二：深度挖掘
对每个重要维度进行针对性搜索，
对重要来源使用 web_crawl 读取全文。

### 阶段三：多源交叉验证
确保覆盖以下信息类型：
- 事实数据（统计、数据、市场规模）
- 案例实例
- 专家观点
- 趋势预测
- 挑战与局限

### 质量检查
开始输出前确认：
- 是否搜索了至少 3-5 个角度？
- 是否读取了最重要来源的全文？
- 是否有具体数据、案例和专家观点？
- 是否探索了正反两面观点？
```

### 模式五：跨 Skill 路由模式

**问题**：用户的请求可能落在两个 Skill 的边界上，Agent 不知道该用哪个。

**解法**：在每个 Skill 的排除条件中，明确指向应该使用的其他 Skill。

```markdown
## 触发与排除

**必须触发：**
- 需要运行代码、生成可执行脚本

**不应触发（技能选择）：**
- 用户只要网页/HTML 交付 → 使用 skill `html-page-generator`
- 用户只要文档(PDF/DOCX/PPTX) → 使用 skill `document-process`
- 只需信息研究，不需要代码执行 → 使用 skill `deep-research`
- 需要部署或管理容器 → 使用 skill `docker-deploy`
```

**为什么关键**：没有明确的排除规则，Agent 遇到"帮我做个 PPT"会同时触发代码执行 Skill 和文档处理 Skill，产生冲突。排除规则让 Skill 之间形成清晰的"职责边界"。

### 模式六：信息收集 + 容错模式

**问题**：工具调用需要多个参数，用户通常不会一次给全。

**解法**：在 Skill 中定义必填/选填参数，以及缺失时的处理策略。

```markdown
## 步骤一：信息收集

| 信息 | 说明 | 是否必须 |
|------|------|----------|
| ZIP 包下载 URL | HTTP/HTTPS 可直接下载 | 是 |
| user_id | 用户标识 | 是 |
| service_name | 容器名称 | 是 |
| 项目类型 | Python/Node.js/Java/Go/静态站点 | 建议 |
| 端口 | 应用监听端口 | 视情况 |

**验证规则：**
- ZIP URL 必须以 http:// 或 https:// 开头
- 缺少 ZIP URL → 询问用户
- 缺少 service_name → 自动推断并确认
```

### 模式七：输出格式强制模式

**问题**：Agent 返回的结果格式不一致，前端无法解析。

**解法**：在 Skill 中严格规定输出格式。

```markdown
## 输出格式规则

生成工具返回包含 download_url 和 filename 字段的结果。
**必须使用标准 Markdown 超链接格式，以 filename 作为链接文本：**

[filename](download_url)

**禁止：**裸露 URL、用自拟文本替换 filename、省略链接。
```

## 四、Skill 的加载机制：从文件到运行时

在生产环境中，Skill 不只是放在文件夹里等着被读取。一个成熟的 Skill 系统有两层加载机制：

### 4.1 静态加载：文件系统

```
app/agents/skills/
├── search_agent/
│   └── deep_research/
│       └── SKILL.md          ← 每个 Skill 一个独立目录
├── code_agent/
│   ├── code-execution/
│   │   └── SKILL.md
│   └── browser-automation/
│       └── SKILL.md
├── document_agent/
│   └── generate_document/
│       └── SKILL.md
└── devops_agent/
    └── deploy/
        └── SKILL.md
```

文件系统加载是最简单的方式：启动时扫描目录，读取所有 `SKILL.md`，解析 frontmatter，注册到内存中。

**适合场景**：开发环境、单机部署、Skill 数量少（< 20）。

### 4.2 动态加载：数据库 + 向量搜索

当 Skill 数量超过 20 个，全部塞进上下文窗口会浪费大量 Token。此时需要"按需加载"：

```
用户输入 → 向量化 → 与所有 Skill 的 description 做相似度匹配
    → 取 Top-K 最相关的 Skill → 注入当前上下文

数据库表结构（示意）：
┌─────────────────────────────────────────────┐
│ skill_configs                                │
├────────────┬────────────────────────────────┤
│ name       │ "deep-research"                │
│ content    │ SKILL.md 的完整内容              │
│ description│ frontmatter 中的 description    │
│ embedding  │ description 的向量表示 (pgvector)│
│ is_active  │ true                           │
│ tools      │ ["web_search","web_crawl"]      │
└────────────┴────────────────────────────────┘
```

**工作流程**：
1. 将每个 Skill 的 `description` 文本向量化，存入向量数据库
2. 用户输入到来时，将输入文本向量化
3. 在向量空间中做最近邻搜索，找到最相关的 Skill
4. 只将匹配到的 Skill 内容注入 Agent 的上下文窗口
5. Agent 按照注入的 Skill 指令执行操作

**为什么 description 写得好至关重要**：向量搜索匹配的是 description，不是 Skill 正文。description 写得模糊，用户说"帮我搜一下这个公司"时就匹配不到 `deep-research` Skill，Agent 就会"裸奔"——没有任何操作指南地去胡乱搜索。

## 五、写好 Skill description 的黄金法则

description 是 Skill 被选中的**唯一入口**。写得好不好，直接决定 Skill 的触发成功率。

### 5.1 反面教材

```yaml
description: 搜索技能
```

**问题**：太短、太模糊。"帮我查一下这个公司的注册信息"不会匹配到"搜索技能"这四个字。

### 5.2 正面教材

```yaml
description: |
  深度搜索与信息研究技能。当用户需要搜索信息、研究某个主题、
  查找参考资料、了解某个领域、比较多个选项、调查公司背景时触发。
  触发关键词：搜索、研究、查阅、了解、对比、分析、最新消息、
  公司信息、行业报告等。
  在生成内容（报告、PPT、文档）之前需要从网络收集信息时，
  也应先触发此技能。
  不适用于网页交付、文档格式转换或需要真实浏览器交互的任务。
```

### 5.3 黄金法则清单

1. **列举触发关键词** — 用户可能说的自然语言表达，尽量穷举
2. **描述使用场景** — 不只是"搜索"，而是"研究主题、查找参考、比较选项、调查背景"
3. **写明排除条件** — 明确说"不适用于 X"，避免误触发
4. **提及上下游关系** — "生成文档前需要先搜索"，建立 Skill 之间的调用链
5. **控制长度在 3-8 行** — 太短匹配不到，太长向量化后特征被稀释

## 六、Skill 的累积效应：真正的护城河

### 6.1 Skill 数量与 Agent 能力的关系

```
  能力
  ↑
  │                          ╱ 有 Skill 积累的 Agent
  │                       ╱
  │                    ╱
  │                 ╱
  │              ╱
  │           ╱
  │        ╱
  │     ╱─────────────────── 只换模型不积累 Skill 的 Agent
  │  ╱
  └───────────────────────→ 时间
```

一个积累了 200 个精细 Skill 的 Agent，其能力远超那个只是频繁更换底层模型的 Agent。**Skill 是你的资产，模型是你租的工具。**

### 6.2 Skill 复用矩阵

Skill 最强大的特性是**跨 Agent 复用**：

| Skill | 搜索 Agent | 文档 Agent | 代码 Agent | DevOps Agent |
|-------|-----------|-----------|-----------|-------------|
| deep-research | **主技能** | 前置依赖 | - | - |
| document-process | - | **主技能** | - | - |
| code-execution | - | - | **主技能** | - |
| docker-deploy | - | - | - | **主技能** |
| task-dispatcher | 可选 | 可选 | 可选 | 可选 |

同一个 `deep-research` Skill，搜索 Agent 用它做主业，文档 Agent 在生成报告前用它收集素材——Skill 本身不变，只是被不同 Agent 在不同上下文中加载。

## 七、常见反模式

### 反模式一：Skill 中没有排除条件

**症状**：多个 Skill 同时被触发，Agent 不知道该执行哪个。
**修复**：每个 Skill 必须写明"不应触发"的场景，并指向正确的替代 Skill。

### 反模式二：Skill 过于抽象

**症状**：Skill 写"调用搜索工具获取信息"，但没说用哪个工具、传什么参数、结果怎么处理。
**修复**：Skill 必须具体到工具名、参数表、调用顺序。Agent 不需要"灵感"，它需要"指令"。

### 反模式三：Skill 不约束输出格式

**症状**：Agent 每次返回的结果格式不同，下游系统无法解析。
**修复**：在 Skill 中明确规定输出格式，包括正例和反例。

### 反模式四：把所有 Skill 塞进系统提示词

**症状**：Token 用量暴涨，每次调用成本翻倍，且大量 Skill 与当前任务无关。
**修复**：使用向量搜索按需加载，只注入与当前任务相关的 Skill。

### 反模式五：Skill 只写了"做什么"没写"做错了怎么办"

**症状**：工具调用失败后 Agent 陷入死循环或直接放弃。
**修复**：在 Skill 中加入错误处理指南。

```markdown
## 错误处理

| 问题 | 处理方式 |
|------|----------|
| 解析返回空内容 | 请用户确认链接是否可公开访问 |
| 图片未提取 | 切换到 process_document_with_images |
| 生成格式异常 | 检查 Markdown 语法 |
| 用户提供本地路径 | 引导用户上传并获取 URL |
```

## 八、从零开始写一个 Skill 的模板

```markdown
---
name: your-skill-name
description: |
  一句话说明技能用途。
  触发条件：用户说"..."、"..."、"..."时触发。
  不适用于：X 场景（使用 skill `other-skill`）、Y 场景。
---

# 技能标题

## 触发与排除

**必须触发：**
- 场景 A
- 场景 B

**不应触发：**
- 场景 C → 使用 skill `xxx`
- 场景 D → 使用 skill `yyy`

## 工具清单

| 工具 | 用途 |
|------|------|
| `tool_a` | 做什么 |
| `tool_b` | 做什么 |

## 工具详情

### Tool 1: tool_a

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| param1 | string | 是 | ... |
| param2 | int | 否 | 默认值 10 |

## 执行流程

### 场景 A
1. 第一步...
2. 第二步...
3. **停止，等待用户确认**

### 场景 B
1. 第一步...
2. 第二步...

## 质量规则

1. 规则一（不可违反）
2. 规则二

## 错误处理

| 问题 | 处理方式 |
|------|----------|
| 错误 A | 做什么 |
| 错误 B | 做什么 |

## 输出格式

（严格规定返回结果的格式）
```
